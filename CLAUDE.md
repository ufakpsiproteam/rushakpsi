# AKPsi Recruitment Platform — project context

Next.js 16 + Supabase recruitment/rush app for Alpha Kappa Psi (Alpha Phi chapter, UF). Read this before touching auth, signup, or the database — several non-obvious things below aren't visible from the code alone.

## Supabase project

- **Live project**: `himvltqfmbgpbjgbjogt` (`https://himvltqfmbgpbjgbjogt.supabase.co`), org `rdeovehqynjcrhyqgbod`. Created 2026-08-11, replaces an old project (`iptpdgitwwwfeqlvourf`) that this repo has no access to and that no longer matters.
- Schema was rebuilt from scratch by replaying `supabase/legacy/*.sql` + `supabase/migrations/*.sql` directly via `apply_migration` (not through Supabase's normal dashboard/CLI provisioning). **This skipped Supabase's automatic baseline role grants** — `anon`/`authenticated`/`service_role` had zero SELECT/INSERT/UPDATE/DELETE on any table (only TRIGGER/REFERENCES/TRUNCATE), which looked exactly like RLS/session bugs and cost a long debugging session before the real cause surfaced. **Fixed** — baseline grants + `ALTER DEFAULT PRIVILEGES` now in place. If this DB is ever rebuilt from scratch again, grant baseline privileges to `anon, authenticated, service_role` on `public` immediately after creating tables, before assuming anything else is broken.
- `.env.local` needs: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (publishable key works), `SUPABASE_SERVICE_ROLE_KEY` — **must be the legacy JWT-format key** (`eyJ...`, decodes to `"role":"service_role"`). The new `sb_secret_...` format key did not get recognized as service_role by this project's PostgREST layer and caused every server-side insert to fail with a plain RLS-shaped 403 — if that happens again, check this first. Also needs `OPENAI_API_KEY`, `NEXT_PUBLIC_SITE_URL`.
- **Never read `.env.local` or use the service role key without the user's explicit per-turn instruction** — standing rule, not a one-time ask.

## Undocumented schema gaps found this session (all now fixed/rebuilt)

The old project had several DB objects created by hand on the dashboard, never captured in any migration file. Found and resolved:
- `rushees.standing` (text) — never had a `CREATE`/`ALTER` anywhere. Replaced entirely with `invite_only` + `bid_status` (nullable booleans, independently staged/published, DB-enforced sequencing — see `supabase/migrations/20260811_split_standing_into_invite_bid.sql`).
- `applications` table — turned out to be defined in an unread legacy file (`supabase/legacy/supabase-applications-migration.sql`); used verbatim.
- `rushees.gpa` — referenced live in 4+ admin pages, never created. Added as `DECIMAL(3,2)`.
- QR-token check-in system (`check_in_tokens` table + 3 RPCs) — dropped entirely per product decision; it modeled a flow that isn't how check-in actually works. Real check-in is self-serve from `app/rushee/events/page.tsx` (logged-in rushee, own camera, plain RLS insert). Manual attendance (admin/recruitment adding someone without a photo) still exists via `create_manual_attendance`, now with a real server-side role check instead of none.

If another undocumented gap turns up, check `supabase/legacy/*.sql` fully before assuming something needs to be invented — two files in there went unread for most of the session and both turned out to matter.

## Attendance & group management

- **`event_attendance` had RLS enabled with SELECT + INSERT policies only — no UPDATE policy ever existed**, in either `supabase/migrations/*.sql` or the live DB (confirmed via `pg_policy` on project `himvltqfmbgpbjgbjogt`, 2026-08-16). Every admin status write (`updateAttendanceStatus` → approve/reject/remove on `app/admin/attendance/page.tsx`) was a raw client `.update()` that silently matched 0 rows — PostgREST returns no error on a 0-row UPDATE, so the admin UI updated local React state and looked like it worked while nothing persisted. This also blocked `redistribute_event_groups()` (it's `SECURITY INVOKER`, so its internal `UPDATE event_attendance` loop hit the same wall), whether called via the "Refresh Groups" button or the `trigger_event_groups_changed` trigger on `events.number_of_groups`. **Fixed** (`supabase/migrations/20260816_harden_attendance_group_management.sql`) by moving all `event_attendance` writes to `SECURITY DEFINER` RPCs with an internal `brothers.access_level IN ('admin','recruitment')` check — the same pattern `create_manual_attendance` already used — rather than opening a broad RLS UPDATE policy:
  - `update_attendance_status(p_attendance_id, p_status, p_reject_reason)` — replaces the old raw `.update()`; `p_status` is one of `approved`/`rejected`/`removed`.
  - `redistribute_event_groups(p_event_id)` — now `SECURITY DEFINER` with the same auth check (required now that RLS isn't the gate).
  - `set_event_group_count(p_event_id, p_number_of_groups)` — new; changes `events.number_of_groups` and redistributes atomically in one call. Used by the "Change to N groups → Update & Redistribute" control on `app/admin/attendance/page.tsx` (next to "Refresh Groups"). Runs as definer so it doesn't depend on the `events` table's own UPDATE RLS policy — see the flagged gap below.
  - `assign_group_number()` — unchanged logic, added `SET search_path = public`.
- **`event_attendance.status` now has a 4th value, `'removed'`**, distinct from `'rejected'`. `'rejected'` = photo-review rejection during check-in approval; `'removed'` = admin revoking a previously pending/approved attendance later (the "Remove" button). Admin UI shows separate "Removed" vs "Rejected" badges/filters. The rushee-side status derivation (`app/rushee/events/page.tsx`) branches only on `'approved'`/`'pending'` and treats everything else as not-attended, so `'removed'` needed no rushee-side code change.
- **`event_attendance` has `UNIQUE(event_id, rushee_id)`.** Removing (or rejecting) a rushee doesn't delete their row, just changes `status` — so `create_manual_attendance`'s plain `INSERT` would error re-adding someone previously removed/rejected. Fixed (`supabase/migrations/20260816_fix_manual_attendance_readd_conflict.sql`) with `INSERT ... ON CONFLICT ... DO UPDATE`, reactivating the existing row as `'approved'` instead of inserting a duplicate. Their prior `group_number` is left untouched by the upsert — hit "Refresh Groups" if it needs reshuffling.
  - **Gotcha for future RPC changes here**: the conflict target must be `ON CONFLICT ON CONSTRAINT event_attendance_event_id_rushee_id_key`, not `ON CONFLICT (event_id, rushee_id)`. This function's `RETURNS TABLE(..., event_id, rushee_id, ...)` makes those column names into PL/pgSQL variables in scope, which collide with the unqualified column list and raise `column reference "event_id" is ambiguous`. Constraint-name targeting sidesteps it.
- **Side finding, not fixed**: the `events` table's only UPDATE policy (`"Only admins can manage events"`) checks a legacy `user_profiles.account_type = 'brother' AND access_level = 'admin'` model, not the `brothers.access_level` model every other current policy uses. `user_profiles` still exists live with rows in it, so admin edits to events (e.g. changing `number_of_groups` via the Events page "Edit Event" modal, `app/admin/events/page.tsx`) may or may not actually persist depending on whether it's kept in sync with `brothers` — unaudited. The new `set_event_group_count` RPC above sidesteps this by running as definer, but the Events page modal path still goes through plain client `.update()` and hasn't been checked.

## Applications read leak + rushee-delete orphaning (fixed 2026-08-18)

Found and fixed during a functional/security audit (RLS pulled live from `pg_policies` on project `himvltqfmbgpbjgbjogt`, plus a static read of the admin write paths). Both are the same failure shape as the `event_attendance` bug in "Attendance & group management" above — worth checking for again if another migration ever touches RLS on a table with legacy history.

- **`applications` SELECT was world-readable to any brother.** `20260811_security_hardening.sql` §6 tried to drop a policy named `"Brothers can view all applications"` — but the actual permissive policy live in the database was named `"Brothers can view submitted applications"` (it came from `supabase/legacy/supabase-applications-migration.sql`, not from the migration that thought it removed it). `DROP POLICY IF EXISTS` on the wrong name silently no-ops, so the real policy survived undetected until this audit. Its `USING` clause was just `EXISTS (SELECT 1 FROM brothers WHERE brothers.id = auth.uid())` — no leadership check, and despite the policy's name, no `is_submitted` filter either — so *any* brother account (not just leadership) could read every rushee's full application: legal name, phone, UF address, GPA, essay answers. **Fixed** in `supabase/migrations/20260818_drop_legacy_applications_read_policy.sql` (dropped the real policy by its real name). **Verified live** by impersonating a `basic`-access brother (`SET LOCAL request.jwt.claims` inside a rolled-back transaction, no password needed) — went from reading all 3 live applications to 0, while re-running the same check as the admin account still returns all 3, and as the owning rushee still returns their own 1. **Side effects checked, none found**: the two brother-facing pages that query `applications` directly, `app/brother/anonymous-applications/page.tsx` and `app/brother/cuts/page.tsx`, both already gate access to `admin`/`recruitment` access_level or the `recruitment_director`/`professional_team` roles — every one of which already satisfies `fn_is_leadership()`, so neither page lost any access it was supposed to have. No other page reads the full `applications` table outside admin/leadership contexts or a rushee's own row.
- **Deleting a rushee account orphaned the `auth.users` row on every use** — not a race condition, the ordinary single-click path. `app/admin/standing/page.tsx`'s `handleConfirmDelete` used to delete `evaluations`/`event_attendance`/`brother_rushee_interactions`/`applications`/`rushees` **client-side**, then call `/api/admin/delete-user`. That route's first check, `assertTargetIsRushee()` (`lib/server-auth.ts`), does `SELECT id FROM rushees WHERE id = rusheeId` — already empty by the time it ran, so the route always 404'd before ever calling `service.auth.admin.deleteUser()` or writing an audit entry. Net effect on every deletion: the rushee's data was actually destroyed, five tables the client never touched (`starred_rushees`, `personal_notes`, `review_marks`, `letter_reads`, `rushee_standing_staging`) were left orphaned, the admin saw a generic "failed, try again" alert, the `auth.users` row became permanently un-deletable (that email can never sign up again), and nothing was written to `audit_log` for a data-destroying action. **Fixed** — the client (`app/admin/standing/page.tsx`) no longer touches any table itself; it now only calls `/api/admin/delete-user`, whose handler already did every step correctly in the right order (related tables including the five above → the rushee row → the auth user → the audit entry, aborting before touching auth if anything upstream fails) — that route was well-built the whole time, it just never used to get the chance to run. **Verified** by re-reading the resulting code path against the (unchanged, already-correct) route, and `npx tsc --noEmit` is clean. **Not exercised end-to-end** — that requires actually deleting a real `auth.users` row, which wasn't done against any of the existing (possibly still-in-use) test/QA accounts. If you want this proven live rather than by inspection, say so and point at a disposable rushee to delete.

## Auth / signup architecture

- Public signup (`/auth/signup`) only creates **rushees** — hardcoded, not user-selectable.
- Signup goes through `app/api/auth/signup/route.ts` (service-role, server-side, rollback-on-failure) — **not** a direct client `supabase.auth.signUp()` + insert. That direct pattern raced the browser's session-propagation timing and intermittently orphaned `auth.users` rows with no profile. Don't revert to it.
- **Brother accounts only get created via invite** (`/invite/[token]` → `/api/invites/accept`, admin-only to issue). There is currently **no frontend page that calls the invite-creation API** — the admin-side "send an invite" UI doesn't exist yet. This is a real gap, not a bug to fix by guessing the design.
- First admin account was bootstrapped directly via SQL (not through the app, since no admin existed yet to issue an invite): `vp.prodevelopment@gmail.com`. Password was shared once in chat — should be rotated.

## UI theme system

- `app/globals.css` defines the base greyscale token system (`--color-ink`, `--color-surface`, `--color-inverse`, …) plus a `@layer components` block (`.btn`, `.card`, `.stat-tile`, `.nav-tab`, `.badge`, `.modal-panel`, `.input`, etc.) that every screen in the app shares.
- A second theme layer, `.portal-shell`, lives at the bottom of `app/globals.css`. It re-declares the same custom-property names with an AKΨ navy/blue/gold oklch palette and Bodoni Moda / Sora / Nunito type (`lib/portalFonts.ts`), so every shared component class recolors automatically wherever it's applied — no per-page edits needed.
- **Scope**: `.portal-shell` is applied by `app/admin/layout.tsx`, `app/brother/layout.tsx`, `app/rushee/layout.tsx`, and `app/auth/signin/layout.tsx` (each wraps its route group in `<div className="portal-shell">` + renders `<WaveBackground />` from `components/portal/WaveBackground.tsx`). That's the entire authenticated app. Only the public landing page uses just the root `app/layout.tsx` and keeps its own space theme — do not add `.portal-shell` there.
- **The wave background only shows through where a page is transparent.** `.portal-shell` redeclares `--color-canvas: transparent` (it's opaque off-white at the root, for admin/landing-style greyscale). Every page's top-level wrapper must use the `bg-canvas` token (or `.app-shell`) for this to work — a literal Tailwind class like `bg-gray-50`/`bg-white`/`bg-black` on that wrapper is opaque regardless of `.portal-shell` and will silently hide the wave for that whole page. This exact bug hit the entire brother portal once already (every brother page was built with literal grays instead of tokens) — if the wave disappears on some new or edited page, this is the first thing to check, not the wave component itself.
- The old flat grey/black chrome (hardcoded `bg-black`/`bg-gray-*`/`border-black`/`text-white` Tailwind literals) has been retired everywhere except landing. `BrotherNav.tsx`, all 9 files under `app/brother/**/page.tsx`, `app/auth/signin/page.tsx`, and the admin dashboard's stat tiles were rewritten to consume the shared token classes instead (`AdminNav.tsx`/`RusheeNav.tsx` already did). If you touch authenticated-app UI, use the existing component classes (`.btn`, `.card`, `.stat-tile`, `.input`, `.nav-tab`, …) and token utilities (`bg-canvas`, `bg-surface`, `bg-inverse`, `text-ink`, `text-ink-muted`, `border-line`, …) so it inherits the portal palette automatically; don't reintroduce raw black/white/gray literals.
- Nav tab active-state uses a Framer Motion (`layoutId="portal-nav-underline"`) sliding underline, implemented directly in `AdminNav.tsx`/`BrotherNav.tsx`/`RusheeNav.tsx`. Every `.card` and `.stat-tile` also gets a scoped hover lift (`.portal-shell .card:hover` / `.stat-tile:hover` in globals.css) — this applies automatically to any element using those classes, no per-instance styling needed.
- The ΑΚΨ lettermark (`.lettermark` class, used in every nav bar and on sign-in) is set in the display font (Bodoni Moda italic) within `.portal-shell`, not the body sans.
- `AdminNav.tsx` only has 8 links — Review Board (`/admin/cuts`), Bid Night Deck (`/admin/slides`), and Interview Questions (`/admin/interview-questions`) were deliberately moved off the top nav (11 links overflowed into a horizontal scrollbar) and now live as shortcut tiles under "More tools" on `/admin/dashboard`. Don't add them back to `AdminNav.tsx` without addressing the overflow.
- The rushee decision-letter reveal (`components/rushee/DecisionLetter.tsx`, `EnvelopeCard.tsx`, the `letter-reveal` keyframe, `canvas-confetti` logic) was deliberately left alone — it inherits the new portal card colors as a byproduct but its animation/trigger logic is unchanged.

## Post-audit UI fixes (2026-08-22)

Five changes made after a full-cycle recruitment audit (rushee/brother/admin flows walked end-to-end). All are UI/query-level, no migrations:

- **Professional-interview "knows this person personally?" disclosure banner** moved from the `opening` step to the `confirm` step (last screen before Submit) in the interview wizard (`app/brother/interview/[interviewId]/[rusheeId]/page.tsx`, single-page step machine — see `Step` type). The casual-interview conflict-of-interest block stays in `opening`; only the professional one moved.
- **Admin nav "Standings" tab renamed to "Rushees"** (`components/admin/AdminNav.tsx`) — label only, route (`/admin/standing`) and on-page heading unchanged.
- **Resume upload now shows the selected filename** next to the "✓ Resume uploaded" indicator (`app/rushee/application/page.tsx`). Session-only — the original filename isn't persisted to the DB (storage key is still a generated `resume_${timestamp}.pdf`), so it won't reappear after a page reload. If that's ever wanted, needs a new column.
- **Interview-details dropdown bug found and fixed**: `loadInterviewBreakdown()` (in both `app/admin/cuts/page.tsx` and `app/brother/cuts/page.tsx`) used to build each panelist's answer list by iterating over *every* question fetched across *all* of a rushee's interviews (casual + professional combined), instead of just that panelist's own answers. Since `order_index` resets per type, this produced duplicate-looking rows — e.g. a blank "Q1: —" from the wrong type immediately followed by the real "Q1: 0 — e" — visible to any admin/leadership brother who opened the dropdown. Fixed by scoping to `answers.filter(a => a.interview_id === ia.interview_id && a.brother_id === ia.brother_id)` instead of the global question list. Also added a `maxScore` (from `interview_questions.score_options`) so each line reads `Q# - score/max - notes`.
- **Interview breakdown UI restructured**: was a per-rushee toggle living in the admin/cuts overview grid card (visible before clicking into a rushee) with no equivalent on `/brother/cuts` at all. Now: removed from the grid entirely; on both `/admin/cuts` and `/brother/cuts`, opening a rushee's detail modal shows a new "Interview Recommendation" box (same visual pattern as the existing "Evaluation Breakdown" box, right below it) with an averaged Casual/Professional recommendation score, plus a "Show Interview" toggle beneath it for the full per-panelist Q&A. Data auto-loads when the rushee is selected (was previously lazy-loaded only on toggle click).

## Known non-bugs

- Two browser tabs on `localhost` (any ports) share one session cookie — logging into a second account in one tab silently swaps the session for both. Not a server bug, not a data leak. Use separate browser profiles/incognito for simultaneous multi-account testing.

## Still outstanding (not yet fixed, flagged during audits)

- `profile-pictures` (upload path) vs `profile-photos` (read path) bucket-name mismatch in app code — both buckets exist so nothing errors, but uploaded photos likely never display for admins.
- No admin UI to generate brother invites (see above).
- A few legacy trigger functions (`update_vote_counts`, etc.) lack `SET search_path`, a minor advisory-level hardening item, not urgent. (`assign_group_number` and `redistribute_event_groups` were fixed 2026-08-16 — see Attendance & group management above.)
- `events` table UPDATE RLS policy still checks the legacy `user_profiles` model instead of `brothers.access_level` — see Attendance & group management above. Unaudited whether admin event edits (Events page "Edit Event" modal) actually persist today.
- **Event check-in group assignment — reported bug, root cause not confirmed, not fixed.** User observed many rushees self-checking into an event and all landing on group 1 until "Refresh Groups" was clicked, despite `number_of_groups` being set correctly. Live-DB forensics (2026-08-21, project `himvltqfmbgpbjgbjogt`) confirmed `assign_group_number()`'s trigger logic is NOT hardcoded to group 1 — it correctly round-robins `(count % number_of_groups) + 1` and reproduced correctly for 2 of 3 live test events. The 3rd event showed all rows on group 1 despite `number_of_groups=5` at query time — mathematically that only happens if it was `1` at insert time (later edited without a redistribute), or a genuine concurrent-insert race on the trigger's `SELECT COUNT(*)`. Check-in timestamps for that event were 8–90s apart, which argues against a literal race, but there's no state-history/audit trail to settle it either way. User declined the proposed fix (row-locking the trigger + auto-redistribute on group-count edit) for this session — deferred, not implemented. If this recurs, get exact repro steps (was `number_of_groups` ever edited during the test, and in what order relative to check-ins) before attempting a fix.
